## 一、这一轮修掉的

### 1. 成片页有一个永远转不完的圈

**严重度：阻断。** 这是 CI 一直红的根因，也是 1(b) 说的「代码卡住」。

`FilmView.render()` 有三条路径会 `return` 但既不设 `exportURL` 也不设
`errorMessage`。SwiftUI 那边的判断是「两个都为空 = 还在生成」，所以页面
永久停在 `GeneratingFilm`：没有成片，没有报错，没有出口，只能按返回键。

最容易踩到的一条是 `previewMedia.accept(url)` 返回 `false`。
`RoomPreviewMediaScope.accept` 在作用域关闭后一定返回 false 并把文件删掉，
而「退出演示」就会关掉它。所以复现路径是：

1. 首页进「房间演示」
2. 点「聊天」，随便发一条
3. 点「退出演示」
4. 再点「看成片」

→ 转圈，永远。缝片其实成功了，只是成品被拒收然后静默丢弃。

**更正一句之前的判断**：我一开始以为 CI 上 `LocalFormalRoomUITests` 挂就是
这个 bug 导致的，不对。修完之后 CI 还是烧完那 240 秒，日志里四分半钟内
零条 `[stitch] exporting` 也零条 `[stitch] failed` —— 缝片根本没走到导出，
还卡在 `filteredClips`（逐段调色重导出）里，那在没有 GPU 的 runner 上是
软件 Core Image 逐帧跑。那条是算力问题，见下面第 7 条；这个转圈 bug 是
另一件事，它真实存在、用户能踩到，只是不是那条 CI 失败的原因。

**修法**：没有补三个 `errorMessage`，因为这个 bug 的本质是「缺了东西」，
而裸 `return` 不会告诉任何人它缺了。改成一个类型 `FilmRenderOutcome`：
每个 case 要么出片要么说原因，只有 `.superseded` 允许什么都不显示
（那种情况下另一次渲染已经在跑）。`FilmRenderOutcomeTests` 在整个输入空间
上枚举，断言「没有新渲染插队时，屏幕必须变」—— 这就是修之前会失败的
那条断言。

提交：`48b6bc1`

### 2. 设置页有一个开得了、关不掉的通知

**严重度：困惑。** 删掉「通知」那一组时发现的。

`NotificationPrimerView`（拍完之后弹的「开通知吧」）会把
`NotificationPreferences.eveningEnabled` 设成 true。而唯一能把它设回
false 的地方是设置页里那个开关。1.3 把那一组删了 —— 如果只删开关不删
primer，用户就能打开一个再也关不掉的每日提醒。

**修法**：primer 一起删掉。`ReminderService` 和
`SharedActivityNotificationService` 没动，它们各自 guard 在自己的 flag 上，
现在没有任何东西能把 flag 打开，所以永远是关的。

提交：`0f731e2`

### 3. 中文用户点隐私政策会跳到英文页

**严重度：困惑。** 这一轮官网改动带出来的。

`SettingsView.privacyPolicyURL` 写死 `https://1day.liangyue.site/privacy`。
官网在 1.3 把默认语言改成英文之后，那个地址就是英文页了，中文页搬到了
`/zh/privacy`。

**修法**：跟着 `AppLanguage.effective` 走。跟的是 app 语言而不是设备语言，
因为那是这个链接上面一屏就能改的设置。

提交：`0f731e2`

### 4. 粘贴邀请码，剪贴板里没码时什么都不发生

**严重度：无响应（1(b)）。** 审计 4.3，之前标的是「打磨」，但它就是
「点了没反应」。

`JoinInviteSheet` 的粘贴按钮是
`if let pasted = ..., let found = InviteCode.extract(...)`，**没有 else**。
剪贴板是空的、或者里面那条消息不含六位码，按钮就什么都不做 —— 同一个
屏幕、同样六个空格子。用户没法区分三件事：没点到、剪贴板空的、复制错了。

**修法**：加 else，出一句「剪贴板里没有邀请码」。打字会把提示清掉，
因为打字就是对它的回答。

提交：`ff4e321`

### 5. 「加入中」的转圈没有取消、没有超时

**严重度：卡住（1(b)）。** 审计 4.5。

`PlansHomeView` 的 `joining` 是一个全屏 `ProgressView`，没有取消按钮，
`store.joinRoom` 也没有时间上限。码打错了或者没信号，人就抱着一台转到
他强退为止的手机 —— 和 app 卡死没有区别。

**修法**：

- 取消按钮。它不会停掉网络请求，停掉的是「等」—— 卡住的是这一部分。
- 20 秒超时。比慢网下一次健康的加入长得多，比「这 app 坏了」的判断
  来得早。文案是「一直没连上，再试一次？」而不是「失败」，因为我们并
  不知道那个房间存不存在，只知道这一次放弃了。

两者共用一个 `joinAttempt` 计数器。在飞的那次请求动用结果之前先对一下它，
否则一次迟到的成功会把人扔进一个他已经走开的房间。

提交：`ff4e321`

### 6. 一个拨不动、也不切换任何东西的开关

**严重度：死代码。** 做时间轴时发现的。

`StoryViewMode`（时间线 / 网格）是持久化状态，`StoryTimelineView` 存着它、
传给 `TimelineHeader`，而 `TimelineHeader` 收到的是
`showsViewModeToggle: false` —— 唯一持有这个状态的页面从来不画那个开关。
除此之外没有任何东西读它。所以它是一个存了偏好、拨不动、也不改变任何
渲染的枚举。

**修法**：连同 `ViewModeToggle` 和四条相关文案一起删。

提交：`914ae42`

### 7. 建完房间之后没有「现在把码发出去」那一刻

**严重度：困惑（裂变链路）。** 审计 3.1。

房间是空的被创建出来的，这是设计如此：你先建，再邀请。但这两件事之间
没有任何东西说「就是现在」—— composer 关掉，故事页打开，而接下来唯一
必须发生的事变成了头部一个胶囊，跟一列等着被拍的瞬间抢注意力。

**修法**：第一次落到一个你拥有、还没人加入的房间时，问一次。只问一次，
按房间码记，永久记（记在 `UserDefaults`，不是 `@State` —— 故事页每次
导航回来都会重建）。已经有人加入的房间不问。

提交：`6b7061a`

## 三、还开着的

按我的判断排序。都不是这一轮的指令范围，列在这里是为了下一轮有个起点。

### 1. 分享文案依赖 `oneday://` 自定义 scheme（审计 4.6）

`Strings.shareMessageInvite` / `shareMessageCaptured` 末尾都带一行
`oneday://join?code=XXXXXX`。

问题有两层：

- **在微信里不可点。** 微信不会把自定义 scheme 渲染成链接，所以那行字
  对收到邀请的人来说就是一串乱码。而微信是这个 app 最可能的分享渠道。
- **没有回退。** 没装 1Day 的人点了（在能点的地方）什么也不会发生 ——
  没有 App Store 页，没有网页。

修法要配 Universal Link 或者一个 `1day.liangyue.site/join?code=` 的落地页
（官网已经在 Vercel 上，加一条路由不难）。**这条影响裂变，我认为是
剩下这批里最值钱的一条。**

### 2. 七日故事的「接着拍」卡片，按钮还写「继续今天的故事」（审计 7.1）

`StoryCard.footer` 是 `isDone ? watchYourFilm : continueTodaysStory`，
只分「完成 / 未完成」两种。而首页的 hero 是有 `.resume` 这个状态的
（`HomeStories`），上面那行 section label 会写「接着拍」。

所以一个停了三天的七日故事上，标签说「接着拚」、按钮说「继续今天的
故事」—— 而它要开的其实是第 2 天。两句话在同一张卡上互相打脸。

`RoomProgress.slotToOffer(today:)` 和 `offeringToday(today:)` 都已经存在
且行为正确（审计 7.2 实际上修了），缺的只是按钮文案跟着它走。

### 3. 首启没有「先随便看看」的出口（审计 1.1）

`FirstRunOnboardingView` 只有两个按钮：`onCreateStory` 和 `onJoin`。
没有跳过。一个还没决定要不要用这个 app 的人，唯一的前进方式是先建一个
故事 —— 对一个日记类 app 来说，那是要求先承诺再体验。

### 4. 按时间的故事，录制页顶栏写「第 1 天」（审计 5.5）

`RecordClipView.localizedMomentTitle` 的兜底是 `Strings.dayN(day)`，
对按时间的故事（`isTimeOnly`）会渲染成「第 1 天」。而那种故事的格子
不是天，是时段 —— 审计建议的文案是「拍下这一刻」。

注意：`MomentTimeline.title(for:)` 里对同样的情况用的是
`Strings.lockedSlot`（「第 N 个瞬间」），那个是诚实的，因为按时间的
故事确实没有别的名字可叫。两处不一致，改的时候一起看。

### 5. 字幕功能可发现性弱（审计 5.6）

回看页可以给片段写字幕、换字幕底、捏放旋转，1.2 和 1.3 都在这上面花了
不少工。但入口是回看页上的一个图标，没有任何一次引导提到过它。这是
「功能存在但没人知道」类型的问题，不是 bug，量级更接近一次 onboarding
的改动。

### 6. 首启承诺的「3 个瞬间」和海报的瞬间数不一致（审计 1.2）

`createQuickStart` 确实是 3 个瞬间，和首启文案一致。但从「计划」tab 点
一张海报，数量是海报自己的（「完美的一天」是 7 个）。

**1.3 缓解了这条**：新的流程是点海报 → 设置页，而设置页上就列着
「7 个瞬间」和全部题目，在创建之前。所以数量不再是个惊喜。但首启那句
承诺本身还是只说 3。

### 7. `LocalFormalRoomUITests` 假设模拟器是干净的

**两件事，都已定性，都不是产品 bug。**

**(a) 脏模拟器。** 在我这台跑了一整轮手工验证（建过故事、拍过片段、
授过权限）的模拟器上，这个套件挂在 `app.buttons["聊天"].tap()` 之后 ——
聊天页的种子消息「今天的故事拍什么？」15 秒内没出现。`xcrun simctl erase`
之后整个套件通过。这个套件（以及靠 `home-room-demo` 入口的另外三个）
没有「开局清状态」这一步，所以只在干净设备上可靠。CI 每次都是新 runner
所以踩不到，本机重复跑会。下一轮值得给它们加一个
`store.challenges = []` 级别的重置入口。

**(b) 成片那条断言在 CI 上是在量机器。** 修掉无限转圈之后，CI 仍然烧完
240 秒。证据：那四分半钟里零条 `[stitch] exporting`、零条
`[stitch] failed` —— 缝片没走到导出，还在 `filteredClips` 里。
`UITestWait` 自己记着数：两人/三人合成器在这台 runner 上、**上面没有 UI**
的时候要 141.5 秒，而整个套件里最重的媒体测试要 208.7 秒。一个三人
`friendsTogether` 成片再套一层 UI 测试，装不进 240 秒；再往上提上限，
只是把「这个测试到底在量什么」的那个数字往后挪。

**处理**：把成片那一条拆成独立的 `testFormalRoomFilmRenders`，CI 跳过
（workflow 里写了原因），本机跑 —— 本机 20.9 秒。这个套件真正得名的
那些东西（聊天、房间隔离、成员切换）留在 CI 上，92 秒，通过。成片路径
本身在 CI 上有 `VideoStitcherTests` / `SharedRoomFilmTests` /
`DefaultFilmAspectTests` 覆盖；只有 UI 测试能看见的那部分 ——
「看成片」经过真实导航栈到达一支渲染好的片子，以及演示房间的
保存/分享是禁用的 —— 在 Mac 上验。

## 四、只能真机验的（`progress.md` §5）

这几项模拟器跑不了 —— 字幕和片头用
`AVVideoCompositionCoreAnimationTool`，在模拟器的软件渲染路径下会崩，
所以代码里是 `#if !targetEnvironment(simulator)` 包着的。1.3 的改动没有
碰这几条的逻辑，但它们从 1.2 起就没人验过：

| # | 验什么 | 怎么算过 |
| --- | --- | --- |
| 1 | 合拍无裁切 | 两人竖拍合成横版：两个人都完整出画，没切到头；左右留白是各自画面的模糊铺底，不是黑边 |
| 2 | 不串台 | 两个格子之间的缝是黑的，谁的画面都没溢出到对方格子里 |
| 3 | 三滚轮 | 曝光 / 色温 / 对比，-50…+50，中位有刻度；按住看原片；「复位」一次归零三个 |
| 4 | 色温方向 | 往右拧画面变**暖**（不是变蓝）—— 这是最容易写反的一个 |
| 5 | 只动自己 | 合拍成片里朋友的画面跟他拍的时候一样，没被你的滤镜染色 |
| 6 | 双人字幕 | 两人在同一瞬间各写一句，各自显示在自己画面下方；长句截断不溢出格子 |
| 7 | 正常注销 | A 机注销后，B 机看不到 A 的片子和留言；房间还在；owner 名字已抹掉 |
| 8 | 断网注销 | 飞行模式注销 → 明确报错「你的东西都还在」→ 本地故事完好、仍登录 → 联网重试能续删完成 |

`grep StoreKit` 零命中。1.3 明确不做（3(a)/(b)），全部推到 1.4 / 2.0
（4(a)）。记在这里只为一件事：`docs/audit-2026-08-22/monetization-audit.md`
把「一个片段同时投到多个房间」列为 Plus 付费功能，而 1.3 已经把它做成

## 六、1.4 待办（1.3 发版时记下的）

### 1. 一起拍看不到人均进度

`RoomCast.hasFilmed` 是二元的 —— 拍过 / 没拍过。所以共享房间的顶栏
能说「阿雅还没参与」，说不出「小明拍了 2/5」。

已经有的：`MomentTimeline` 的每个节点在共享房间里渲染 `lanes`（每个人
自己那一条）加名字加「还缺你」，所以逐个瞬间是看得到的，只是要一个个
扫。缺的是一次性的答案 —— 顶栏一行人均计数。

不是 bug，是新功能，所以没进 1.3。

### 2. 两种故事用两种列表形态，理由站不住

现状（`StoryTimelineView` 约 212 行）：

```swift
if challenge.isTimeOnly { MomentFilmstrip(...) } else { MomentTimeline(...) }
```

写在代码注释里的理由是「按时间的故事没有名字，竖着列就是一行行空白」。
这个理由有两个洞：

1. **它有名字。** `MomentTimeline.title(for:)` 第 221 行对 `isTimeOnly`
   返回 `Strings.lockedSlot`（「第 N 个瞬间」），`icon(for:)` 返回
   `camera.fill`。两个 fallback 都写好了、都能用，而 `StoryTimelineView`
   从不把按时间的故事送进来 —— 是一段绕过去的死代码。
2. **两种故事结构完全一样。** `cardCount(for:)`（第 763 行）在没有题目时
   返回 **7**。所以按时间的故事也是 7 个固定格子、有序、每个要么拍了
   要么没拍，和有主题的故事一模一样。唯一的区别是格子上有没有名字。

结构相同却给两种形态，学习成本翻倍，代码路径翻倍。

**1.4 的两条路：**

- **A（便宜）** 两种都走 `MomentTimeline`，删掉 `MomentFilmstrip.swift`
  和那个分支。已有的 fallback 直接生效：按时间的行读「第 3 个瞬间 ·
  14:20」，有主题的读「咖啡 · 14:20」。约 1 小时，是删代码不是加代码。
- **B（真正的问题）** 按时间的故事本来就不该有 7 个预设空格子。
  「发生什么拍什么」的故事应该是拍一段长一格。那样帧带才真的对 —— 它是
  一份记录，没有空格子 —— 竖轨才真的只属于有计划的故事，两种形态才第一次
  代表两件不同的事。代价是数据模型：`cardCount`、`saveClip` 的追加、
  拼接对格子数的假设，以及 `isComplete`（会长的故事永远不完成 → 触发
  成片那条链会断）。不是一次小改。

A 是止血，B 是治因。先 A 再看要不要 B。
