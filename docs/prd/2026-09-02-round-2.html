1背景

① 自由拍摄会真的丢片 严重度最高

先更正一条我上一轮写错的判断

上一轮 PRD 把原因写成「onSave 是空闭包」——这是错的。自由拍摄走的是 showSavePicker → store.saveClip（RecordClipView.swift:255）， CameraTabView 里那个空 onSave 在这条路径上从不被调用。

真正的机制是：片子先录进 FileManager.default.temporaryDirectory （ClipRecorder.swift:215），只有归档成功才落盘。

两条路会走进死胡同，各自只弹一句 toast 就没有下文：

录完→一个计划都没有→toast「先建个计划」→ 只能重拍或离开→片子没了
录完→画幅跟所有计划都不匹配→toast 提示→ 同上

CameraTabView 一 unmount，recorder.clipURL 就没了，temp 文件被系统回收。 没有草稿箱，也没有离开前的挽留。

② 首页挑错「今天的故事」

RootShellView.swift:31 用 .min { $0.recordedCount < $1.recordedCount } 选 hero ——谁拍得最少谁赢。于是一个躺了三天没动的空故事，永远压着今天真正在拍的那个。

Cassie 最早那条「9.1 的内容没在首页看到」就是这行造成的：真机截图里「和我过一天 0/7」占着 「今天的故事」，9.1 那个（1/7）被挤到「其他的故事」。上一轮加的日期行只让人看得出今天是几号， 没解决选谁。

③ 首页没有按天回看的入口

只按「进行中 / 已完成」分组。上一轮的日期行回答了「今天是几号」，没回答「怎么翻回 8.31」。

④ 新建故事页层级多了一层 Cassie review 发现

上一轮 PR-3 加的题目预览条，让题目在同一屏出现了两次；而「主题挑战」那张卡其实是个 伪装成选项的分类标签——底下的推荐网格本身就是主题挑战。

真实结构只有一层

有 N 个模板。其中一个（和我过一天）没有题目，其余的各有 7 个。
双卡把这件事表达成了两级选择。这是上一轮「两套选择器」问题的更深版本——PR-2 让两套互相一致了， 但没问该不该有两套。那是个局部最优。

2目标 / 非目标

目标

  1. 录完的片子不会无声消失 —— 任何路径上，用户都得先做个决定才可能丢掉它。
  2. 首页顶上那块永远是「此刻最该动的那件事」，且它说的话跟它显示的东西一致。
  3. 新建故事页只有一层选择，题目只出现一次。
  4. 能按日期翻回过去的故事。
  5. 用 AI 解掉「这天还没过完，我怎么知道该写哪 7 个题目」——Cassie 最早提的第 5 条。

非目标

  • 不做云端草稿同步（草稿只在本机）。
  • 不改录制本身（画幅、时长、水印都不动）。
  • 不做跨故事的片子搬家。
  • 不做 AI 剪辑、不做视频内容理解（vision）。
  • 不做草稿自动过期清理（本轮只手动删）。
  • 不做新产品（多人同场景按脚本拍）——判断见 §12。

6.1 选择规则（按顺序，第一条命中即止）

#条件结果
1未完成，且满足其一：
· 一日故事：startDate 是今天
· 七日挑战：currentDay 落在 1...cards.count 内
多个命中时取最近活动的 （cards.compactMap(\.recordedAt).max()，都没拍过则按 startDate 新的优先）		 .today
2a12:00 前，且存在「昨天开始且没拍完」的故事.resume(它)
2b12:00 前，无昨日残留.startToday
2c12:00 及以后，有未完成的.resume(最近活动的)
3都不命中.startToday

两个容易搞错的地方

① 七日挑战跨天是常态。它 startDate 在一周前，但今天正是第 4 天 ——这种不能算旧故事，它就是今天该拍的。所以规则先按 currentDay 判七日，再按 startDate 判一日。

② 「12:00 前有昨日残留就 resume」是 Cassie 定的。 理由：昨天的事没做完，早上不该假装是新的一天。

10PR-10 · 说一句今天要干嘛，题目自己出来

PR-10feat: 说一句今天要干嘛，题目自己出来 第一个 AI feature

解的是 Cassie 最早提的第 5 条：「自己写 7 个瞬间，如果没经历今天的这一天，写的会不会很突兀」。 突兀感的来源是「这天还没发生，我怎么知道会有哪 7 个瞬间」—— 而「今天要搬家」这句话现在就说得出来。

10.1 交互

自己写题目→说说今天要干嘛→ 「今天要搬家」→7 个题目填进可编辑列表→逐条改
  • 入口，不是新层级：挂在现有「自己写题目」下，现有的手写和题库两条路都留着 —— AI 是第三个开头，不是替代。
  • 生成结果直接填进 GuidedMomentsView 现有的可编辑列表，用户能逐条改。
  • 失败要静默降级：没网 / 超时 / 后端挂了 → 直接退回手写，不弹错误。 这个 feature 是个加速器，不是必经之路。

10.2 key 策略：极小后端代理 Cassie 已定

为什么不能把 key 打进 app

打进 app 的 key 会被扒出来。所以走一个只转发一种请求的函数：

  • 端点只接受「一句意图」，只返回「N 个题目字符串」。不做通用 LLM 代理。
  • 带速率限制（按设备标识，不需要账号）。
  • 调用量天然极低 —— 只在建故事时调一次，不是每次打开 app。成本可控。
  • 后端不存用户输入（那句话可能很私人）。

本地开发的地理限制

Anthropic API 在 Cassie 本地需要走代理（403 geo-block）。这影响开发调试， 不影响线上用户（服务器不在这儿）。实施时本地测试要记得开代理。

10.3 埋点 —— 这个 PR 真正的产出

PR-10 除了功能，还要验证一个假设：AI 生成的拍摄指令，人愿意照着拍吗？ 这是 Cassie 那个新产品想法的核心前提（见 §12）。所以要记：

  • 生成了几次 / 采纳了几次（进到 setup step 算采纳）
  • 7 条里改了几条（改写率）
  • 改的是哪几个位置（前面的还是后面的）

本地统计即可，不需要上报服务器。

  • PromptSuggestionServiceTests：正常响应解析出 N 条；返回畸形 JSON 时抛错不崩； 超时按失败处理；失败路径不改动用户已填内容。

关于那个新产品想法

Cassie 提到：用户说想拍什么 → AI 生成脚本 → 大家一起去拍 → AI 剪辑， 并自己判断「可能不是一个产品」。这个判断是对的。

1Day新想法
动机把今天留下来（记录）我想做一支片子（创作）
尺度一天，被动等瞬间发生一次拍摄，主动安排
拍砸代价无所谓，反正是日常浪费了所有人的时间
「一起」各拍各的，同一天的拼在一起同一个现场，按脚本分工
成片形态固定：7 段按顺序接起来脚本决定：有长有短、有镜头语言

最后一行是根本区别。VideoStitcher 现在是确定性的顺序拼接。

两个反直觉的判断：

  • 最可能死掉的一环不是 AI，是「大家一起去拍摄」。约几个人在同一时间同一地点照着脚本拍东西， 社交协调成本极高。这是第一个该验证的假设，不是最后一个。
  • AI 剪辑可能根本不需要 AI。如果脚本是结构化的（第几个镜头拍什么）， 「剪辑」就退化成按脚本顺序拼 —— 正是 1Day 已经在做的事。

路径：PR-10 就是这个新产品的最小验证。它测的正是核心假设 「AI 生成的拍摄指令，人愿意照着拍吗」。假设不成立 → 只花一个 feature 的成本就知道了； 成立 → 手上有真实的采纳率和改写率数据，做新产品时不是在猜。
