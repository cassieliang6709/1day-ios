0这轮为什么基在 demo/tonight 上

反馈是对着 build 9 提的，build 9 出自 demo/tonight。而 main 落后它 56 个提交——第 3 条要改的 StoryNextUp.swift、第 4 条相关的 RoomRoster.swift、滤镜的 LookPanel.swift，在 main 上根本不存在。基在 main 上等于对着一份两周前的代码修今天的 bug。

所以这八条全部 --base demo/tonight。代价是 main 和 demo 的距离还会拉大。

欠着的账

#3 到 #12 共 10 个 PR 全部 open，一个没合。CI 从 8 月 21 日红到 9 月 2 日才修好，所以这批 PR 谁也没被真正验证过就堆在那里。这轮做完，该做的是把 PR 栈合掉，不是继续往上堆。

1模板存进库，并且有封面

「一个是用户创建好的模版，可以保存在模版库（跟着题目拍下面），自己上传封面 或者 系统匹配封面」

三件事，得分开看

要求现状要做的
自建模板存进模板库 已有 customTemplates.v1 这个持久化 key，和 updateCustomTemplate。先确认是不是已经能存了——如果能，说清楚，不要修一个不存在的 bug 确认后补齐缺的那一段：建完能在创建故事时再选到
跟着题目拍 选模板后拍摄页是否显示该模板的提示词，待确认 每个瞬间显示它自己的题目
封面 故事有 coverURL（StoryCard / TemplateCard），模板没有 两条路都要：相册上传，和按内容自动匹配

自动匹配不联网

MomentCatalog 里已经有一套「提示词 → 图标」的映射，自动封面走它就够了。这个应用已经有一处联网（提示词建议走 Cloudflare Worker），封面再加一处网络依赖不值得——封面失败会让整张卡片空掉，而提示词失败只是少几行建议。

落盘要过边界

用户上传的封面存 Documents，写法照 ClipFileStore：一个 protocol 定义目录结构，View 层不碰 FileManager。这条不是洁癖——片子的落盘就是这么做的，两套写法会让「文件到底在哪」变成没人答得上来的问题。
如果要读相册，ios/project.yml 里得补 NSPhotoLibraryUsageDescription（现在只有 ...AddUsageDescription，那是「写」的权限）。

2没拍过的故事也得看得见

「创建好的内容，即使没有拍，应该也能在我的故事里看到。」

这条我没能确认根因

读代码读不出来它为什么会不可见，所以这条的第一步是写一个失败的测试把它复现出来，不是照着猜测改。如果查下来发现故事其实一直可见、问题在别处（比如标题不对导致没找到），就如实说，不要为了交差硬改一版。

三个嫌疑

位置为什么可疑
StoryTimeline.swift 本身没有按 clip 数过滤，理论上未拍的故事应该出现。所以问题多半不在这
HomeHeroChoice.swift filter { !$0.isComplete && !$0.cards.isEmpty } — 注意是 cards（瞬间槽位数）不是 clip 数。什么样的故事会造出 0 个 card？time-only？自由拍摄？自建模板？
PlansHomeView.swift 标题是 timeline.includesToday ? yourStories : scrollBack。「我的故事」这四个字只在列表里有今天的东西时才出现，否则叫「往回翻」。而且 hero 会被从列表里 excluding 掉——故事被提到顶上当 hero 了，列表里自然就没有

判据：任何已创建的故事，无论拍没拍，都必须在首页某处可见、可点进去，并且那块区域的标题得说人话。

3一个故事可以跳着拍

「进入模版页，如果是故事，可以跳着拍，所以蓝色的框的思路可以重新理（现在是下一个，我觉得逻辑不对）」

上一轮做了 #9「一天只该有一件下一步的事」，产物是 StoryNextUp.swift + StoryAgenda.swift：故事页上一个蓝色高亮框，指着「下一个该拍的」。

这是上一轮的方向做反了，不是实现有 bug

「只有一件下一步的事」解决的是选择过载——当时屏幕上每个瞬间下面都挂着一张「等待 Leo」的卡，三个朋友五个瞬间就是十五张卡。收敛成一件事是对的。

但收敛的方式把一个自由的顺序说成了一条流水线。一天里的七个瞬间没有先后依赖，谁先谁后是拍的人当下的事。用最重的视觉（蓝色描边）独占一个槽位，等于告诉人「别的还不能拍」。

改完该是什么样

  • 每个没拍的瞬间平等可点，点哪个拍哪个。没有一个看起来是锁住的
  • 「下一个」降级成弱建议——一个轻提示，或者进页面时默认滚到那儿。不能是唯一入口
  • 拍过的和没拍的，一眼能分开
  • StoryAgenda 的 API 跟着从「命令」改成「建议」，StoryAgendaTests 一起更新

代码里其实已经承认了这件事

RoomCast.swift 的注释白纸黑字写着 「Which moment they film is theirs to pick」——房间里每个人自己挑拍哪个。这句话在数据层是对的，只是界面层没跟上。这次是让界面追上数据，不是改主意。

4还没建的房间，不能说「已有 3 人」

「和朋友一起，为什么现在显示了有3人，（周悦林，房间已有三人）这个UI不对。」

根因

// StoryComposerView.swift:311 private var knownFriendNames: [String] { var seen: [String] = [] for challenge in store.challenges where challenge.isShared { for member in store.members(for: challenge.id) where !seen.contains(member.name) { seen.append(member.name) } } return seen }

它把你已有的所有房间里见过的人捞出来，传给 SetupStep.memberNames，渲染成一排头像 + Strings.membersInRoom(count) = 「房间里有 3 人」。

意图是「建议」，措辞是「事实」

原始注释写的是 shown as suggestions … so it isn't an empty promise——作者知道这是建议。但界面上写的是「已有」。一个还没创建的房间被说成已经有三个人，而那三个人根本不知道这件事、也不会自动进来。这不是措辞小问题，是界面在承诺一件不会发生的事。

两条路，选一条

方案做法代价
删掉新建房间时这排头像和这句话直接不出现少一点「和朋友一起会是什么样」的暗示
说实话改成「上次和你一起拍的人」，头像可点 = 真的发邀请点了必须真的发出邀请。做不到就别做成可点的，那只是造第二个假承诺

注意别误伤：RoomCast.rosterLine 用的 Strings.peopleInRoom 是真实房间的人数，那个是对的。

5自由拍摄那块，三个元素里两个在说谎

「自由拍摄下面有一个瞬间1，我感觉界面不好，我下面有三个白色的横跳，这个的设计是什么，原理是什么。」

直接回答：它没有原理

// CameraComponents.swift，约 163–174 行 Capsule().fill(.white.opacity(0.42)).frame(width: 34 * scale, …) Capsule().fill(.white) .frame(width: 46 * scale, …) Capsule().fill(.white.opacity(0.42)).frame(width: 34 * scale, …)

三个写死的胶囊。永远三条、永远中间那条亮。跟这个故事有几个瞬间、你在第几个，完全无关。它长得像进度指示器，但它不指示任何东西。

「瞬间 1」更糟

自由拍摄走 RootShellView.swift 的 CameraTabView，那里 day: 1 是硬编码的。自由拍摄的片子还没归进任何故事，「瞬间 1」是句假话。

元素说的实际
「自由拍摄」这是自由拍摄真的
「瞬间 1」这是第 1 个瞬间假的 — 还没归进任何故事
三条白杠共 3 步，当前第 2 步假的 — 写死的装饰

判据：这块区域里的每个元素，要么说真话，要么删掉。进度指示器要么按真实瞬间数和当前位置画，要么删；自由拍摄模式下「瞬间 N」不该出现。

6拍摄时看得见的，成片里得有

「右上角的logo如果不能保存在最后渲染拼接的页面，那就没有意义。我的想法是拍摄的时候看不见，或者在拍摄页能不能做几个类似tiktok的贴纸的功能，可以切换贴纸（不过这个优先级没那么高）」

先纠正一个位置

东西在哪进成片吗
1Day logo 牌（BrandStamp）拍摄页左上不进
日期 + 时间拍摄页右上待核对 addCaption
「made with 1Day」水印成片左下进（真机）

用户记的位置有出入，但判断是对的：拍摄时看到的那个 logo 牌子，和成片左下角的水印是两个东西，前者永远不会出现在成片里。

方向已定：拍摄时看不见

贴纸功能用户自己标了「优先级没那么高」，这轮不做。这轮只做一件事：把拍摄页上进不了成片的装饰拿掉，并把其余元素跟 VideoStitcher.addCaption 逐个核对，列一张对照表。

保守优先——倾向于从拍摄页拿掉说假话的元素，而不是给成片加一堆新叠加层。成片的叠加层是最贵也最容易出事的一层。

这条在模拟器上验不了

VideoStitcher 里所有叠加层都被 #if !targetEnvironment(simulator) 包着（约 140 / 178 / 223 行）——AVVideoCompositionCoreAnimationTool 在模拟器上不工作。模拟器导出的成片本来就没有任何叠加层，看到「成片很干净」不能推出「水印没生效」。
涉及成片外观的结论，只能靠读代码，结论里必须写明「未在真机验证」。

8房间功能，得真的测一遍

「测试好房间功能。」

房间功能已经两周多没被任何自动化验证过

四个 CloudKit suite（CloudKitIdempotency / CloudKitPagination / RoomSyncIntegration / JoinedRoom）在 CI 上是被 -skip-testing: 跳掉的。

原因是一条连锁：CI 用 CODE_SIGNING_ALLOWED=NO 编译 → 没有 iCloud entitlement → CKContainer.accountStatus() 直接打死 test host（不是抛错，是进程没了）→ 连「跳过」的机会都没有。

叠加上 CI 从 8/21 红到 9/2，房间这块确实处于无人验证状态。

这轮的交付，报告比代码重要

做什么说明
判断本机能否真跑那 4 个 suite只读判断模拟器 iCloud 状态。不代替用户登录 iCloud，不输入任何 Apple ID / 密码 / 验证码。跑不了就说清楚卡在哪一步
补齐脱网可测的那一层邀请码规范化与校验、深链 oneday://join 的合法与非法解析、RoomCast（我永远第一个且只一次；本地 clip 算我的）、RoomProgress、recordedClips 本地优先合并、signOut 清缓存、recordName 推导稳定
列出仍然没有覆盖的行为这是最有价值的产出——诚实列出哪些房间行为至今没有任何自动化保护
核实 Production schema只读。已知阻塞项：Development 有、Production 没有，正式包的房间会全挂

不许为了变绿而放宽断言

这条任务的价值全在「知道哪里没测到」。一个绿色但空心的测试套件，比一个诚实的缺口清单危险得多。

9一条贯穿八件事的判据

把八条摆在一起看，第 2、4、5、6 条其实是同一个毛病的四个切面：

#界面说的实际
2（故事不在列表里 ⇒）你没有这个故事故事在，只是没显示
4房间里有 3 人房间还不存在
5瞬间 1，共 3 步写死的装饰
6你的片子上有这个 logo成片里没有

判据

界面上出现的每一个数字、每一句话、每一个进度条，在它出现的那一刻必须是真的。做不到就删掉——一个空位比一句假话诚实。

这四条单看都是小 bug，凑在一起是同一件事：这个应用有几处在为了看起来完整而说话。装饰性的进度条、猜测性的人数、进不了成片的水印，都是同一个冲动的产物。
